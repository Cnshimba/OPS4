1. Capstone Architectural Blueprint & Baseline (Labs 1–3)

In high-performance computing, the physical or virtual hardware is merely the canvas. The real engineering begins when multi-tenant schedulers, secure cryptographic inter-node authenticators, and high-speed message-passing frameworks coalesce into a unified execution fabric.

1.1 The Provided Baseline Cluster

For this capstone, student pairs are provided with a pre-configured 5-node Rocky Linux 9.6 cluster. The architecture comprises:

  • 1 Master Controller Node (master): 4 GB RAM, 2 vCPUs, hosting slurmctld, the NFS export server (/shared), and Chrony local time server.
  • 4 Compute Worker Nodes (compute01–compute04): 2 GB RAM, 2 vCPUs each, running slurmd, mounting master:/shared, and syncing clocks via server master iburst.
  • Private Network Subnet: 192.168.56.0/24 with static entries in /etc/hosts.
  • Munge Cryptographic Layer: Symmetric 1024-byte key (munge.key with permissions 400, owned by munge:munge) authenticating RPC payloads between the controller and workers.
  • Slurm Workload Manager: Partition debug configured in slurm.conf with ReturnToService=2, keeping all worker nodes in the healthy IDLE state.
  • Open MPI 4.1.x & PMIx: Wrapper compilers (mpicc) and runtime daemons tightly linked to Slurm via PMIx.

🔍 Verification Command

Always run sinfo and srun -N 4 hostname before starting. If any node is marked DOWN or DRAIN, check Munge service state (systemctl status munge) and resume the node via scontrol update NodeName=compute0X State=RESUME.

2. Compiling the Production Scientific Stack (Lab 4)

Generic Linux distribution RPM packages are compiled for baseline x86-64 compatibility, sacrificing vectorization instructions like AVX-2, AVX-512, and FMA. Production HPC administrators compile domain-specific math and data libraries directly from source on shared storage (/shared/apps/).

2.1 The Dependency Hierarchy

Software packages must be compiled in strict hierarchical dependency order:

  1. OpenBLAS: Base linear algebra (BLAS/LAPACK). Compiled with DYNAMIC_ARCH=1 USE_OPENMP=1. Dynamic architecture detection compiles optimized kernels for all major CPU microarchitectures, selecting the fastest vector units at runtime.
  2. FFTW 3: Fast Fourier Transform library. Configured with --enable-shared --enable-mpi, wrapping discrete spectral transforms into distributed MPI communicators.
  3. Parallel HDF5: Hierarchical Data Format for parallel I/O. Compiled with CC=mpicc ./configure --enable-parallel --enable-shared, routing dataset writes through collective MPI-IO.
  4. ScaLAPACK: Distributed-memory dense linear algebra. Solves linear systems using 2D block-cyclic matrix distribution across MPI ranks. Configured via CMake explicitly pointing -DBLAS_LIBRARIES and -DLAPACK_LIBRARIES to your custom OpenBLAS.
  5. PETSc: Portable, Extensible Toolkit for Scientific Computation. Provides parallel nonlinear and PDE solvers. Links Open MPI, OpenBLAS, ScaLAPACK, and HDF5 concurrently.
Compiler Flags & Shared NFS Targets 
# OpenBLAS
make -j2 DYNAMIC_ARCH=1 USE_OPENMP=1
make PREFIX=/shared/apps/openblas install

# FFTW 3 (Requires MPI module loaded)
module load mpi/openmpi-x86_64
./configure --enable-shared --enable-mpi --prefix=/shared/apps/fftw3
make -j2 && make install

# Parallel HDF5
CC=mpicc ./configure --enable-parallel --enable-shared --prefix=/shared/apps/hdf5
make -j2 && make install

# ScaLAPACK (CMake linking to OpenBLAS)
cmake .. -DCMAKE_INSTALL_PREFIX=/shared/apps/scalapack \
         -DBUILD_SHARED_LIBS=ON \
         -DLAPACK_LIBRARIES=/shared/apps/openblas/lib/libopenblas.so \
         -DBLAS_LIBRARIES=/shared/apps/openblas/lib/libopenblas.so
make -j2 && make install

3. Lmod Environment Modules & Centralized mpi4python (Lab 4)

3.1 Dynamic Lmod Lua Modules

Static environment variable manipulation in /etc/profile.d/ leads to dynamic linker collisions. Lmod mutates shell paths on a per-session basis via declarative Lua modulefiles stored in /shared/modulefiles/.

Each Lua file must prepend runtime directories:

Sample: /shared/modulefiles/openblas/0.3.26.lua 
local base = "/shared/apps/openblas"
prepend_path("PATH", base .. "/bin")
prepend_path("LD_LIBRARY_PATH", base .. "/lib")
prepend_path("C_INCLUDE_PATH", base .. "/include")
setenv("OPENBLAS_DIR", base)

3.2 Centralized Python Environment & mpi4py

Instead of fragmented local Python user directories (~/.local), a cluster requires a single source of truth on the shared NFS mount (/shared/apps/python-hpc-env):

  1. Instantiate the virtual environment: python3 -m venv /shared/apps/python-hpc-env.
  2. Direct pip compilation via site.cfg to force NumPy to link against your optimized OpenBLAS library rather than slow system fallbacks.
  3. Compile NumPy using pip install --no-binary :all: numpy==1.26.4 and confirm linking with python3 -c "import numpy; numpy.show_config()".
  4. Compile mpi4python (mpi4py) against the cluster's Open MPI headers, enabling high-performance parallel message passing directly in Python.
  5. Provide /shared/modulefiles/python-hpc/1.0.lua to inject the virtual environment and its optimized libraries across all nodes.

4. Cluster Performance Benchmarking & Linpack Tuning (Lab 6)

Cluster performance evaluation centers on High-Performance Linpack (HPL), the benchmark governing the global Top 500 list of supercomputers. HPL measures the rate of execution of dense linear systems (Ax = b) using LU decomposition with partial pivoting.

4.1 Theoretical Peak (Rpeak) vs Sustained (Rmax)

To evaluate efficiency, compute the theoretical upper bound of hardware floating-point operations:

$$R_{peak} = \text{Nodes} \times \frac{\text{CPUs}}{\text{Node}} \times \text{Clock Frequency (GHz)} \times \frac{\text{FLOPs}}{\text{Cycle}}$$

Rpeak = 4 × 2 × 2.4 × 4 = 76.8 GFLOPS

The Cluster Efficiency (E) represents the percentage of theoretical capability achieved in practice:

$$E = \left(\frac{R_{max}}{R_{peak}}\right) \times 100\%$$

4.2 Tuning HPL.dat Parameters

  • Problem Size (N): Determines matrix dimensions. Sizing N to consume 80% of aggregate physical RAM is essential to keep the CPU execution units saturated while preventing disk swapping: $$\text{Memory (GB)} = \frac{N^2 \times 8 \text{ bytes}}{1024^3} \implies N \approx \sqrt{\frac{\text{Target RAM (Bytes)}}{8}}$$ For 4 compute nodes with 2 GB RAM each (~6 GB usable total), setting N ≈ 25,000 achieves near-optimal memory footprint.
  • Block Size (NB): Governs cache block-cyclic decomposition. Optimal range is 128 ≤ NB ≤ 256.
  • Process Grid (P × Q): P × Q must equal the total number of Slurm MPI tasks (8 ranks: 4 nodes × 2 tasks/node). Standard tuning favors P ≤ Q with Q approximately 2 × P (e.g., P=2, Q=4).

5. Distributed MPI Parallel Programming (Chapter 8 Workbook)

Distributed-memory architectures do not share physical RAM; processes communicate by passing messages over the network using Message Passing Interface (MPI) primitives.

5.1 Communication Primitives Comparison

Primitive Type Scope Primary Function
MPI_Send / MPI_Recv Point-to-Point Rank-to-Rank Transmits data buffer directly to specific destination rank with matching tag.
MPI_Barrier Synchronization Communicator Blocks all processes until every rank in the communicator reaches this call.
MPI_Bcast Collective One-to-All Broadcasts identical buffer from root rank to all other ranks.
MPI_Scatter Collective One-to-All Partitions an array on root into equal contiguous chunks, distributing one chunk per rank.
MPI_Gather Collective All-to-One Collects local arrays from all ranks into a single contiguous array on the root rank.
MPI_Allgather Collective All-to-All Collects local data from all ranks and delivers the complete dataset to EVERY rank (no root parameter).
MPI_Reduce Collective All-to-One Aggregates distributed partial values to root using an associative operator (MPI_SUM, MPI_MIN, MPI_MAX).

5.2 Common MPI Pitfalls

  • Deadlock: Calling blocking MPI_Send on two nodes simultaneously waiting for reciprocal MPI_Recv calls, or mismatching message tags.
  • Buffer Sizing in Scatter/Gather: The sendcount and recvcount parameters refer to the number of elements sent/received per process, NOT the global total count.
  • Slurm Allocation Requirements: Attempting to invoke mpirun outside an allocated Slurm partition causes "not enough slots available" errors. Always execute via srun or inside an active salloc session.

6.1 Rapid Ingestion & Compilation Playbook

Compilation & Slurm Submission Cheatsheet

# Case 3: C + Parallel HDF5

6.2 Demonstration Protocol Checklist

  1. Ensure both partners are logged into the cluster and have active terminal tabs ready.
  2. Confirm sinfo displays 4 idle nodes and pdsh -R ssh -g compute hostname responds instantaneously.
  3. When the lecturer delivers the source code, copy it directly to /shared/ so all nodes have immediate access.
  4. Identify the mathematical or I/O library required and execute module load <library>.
  5. Compile the binary using the wrapper (mpicc, h5pcc) and link the matching library flags.
  6. Dispatch via Slurm requesting 4 nodes: srun -N 4 -n 4 <binary> or sbatch submit_job.sh.
  7. Verbally explain the rank output, reduction aggregation, and how Lmod resolved dynamic libraries across nodes.
