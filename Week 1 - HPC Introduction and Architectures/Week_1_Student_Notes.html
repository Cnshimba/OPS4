1. Introduction to HPC

Let's get one thing straight from the start: High Performance Computing isn't just about having "fast computers." It's the science and engineering of pooling computing power together — hundreds or thousands of machines working as one — to tackle problems that no single desktop or server could ever handle alone (Sterling et al., 2018).

1.1 The Need for Speed (and Scale)

In everyday IT, we tend to think about throughput: how many web requests can a server handle per second? HPC flips the question. Here, what matters is Speedup — how much faster can we solve a single, massive problem by splitting the work across multiple processors?

The real world makes the case better than any textbook. Training large AI models like GPT takes thousands of GPUs crunching through petabytes of text in parallel. In medicine, assembling a complete human genome and hunting for cancer mutations requires raw computational muscle that a single workstation simply can't provide. On the Johannesburg Stock Exchange (JSE), high-frequency trading algorithms analyse market data in microseconds. And right here at home, the South African Weather Service (SAWS) runs daily weather simulations — solving Navier-Stokes equations across a grid covering the entire country — to issue storm warnings.

1.2 Local Context: The South African Cyberinfrastructure Ecosystem

You might think supercomputing is a first-world luxury, but South Africa actually hosts the most advanced research computing infrastructure on the continent. It's all coordinated under the National Integrated Cyber Infrastructure System (NICIS), which stands on three pillars (CHPC, 2024):

  • CHPC (Centre for High Performance Computing): Located in Cape Town. Their flagship system, Lengau, is one of the fastest supercomputers in the Southern Hemisphere and is available to SA universities — including VUT.
  • DIRISA (Data Intensive Research Infrastructure of South Africa): Handles long-term storage and curation of massive scientific datasets (such as radio astronomy from the Karoo).
  • SANReN (South African National Research Network): High-speed 100Gbps fibre backbone moving terabytes between campuses and national supercomputing facilities without bottlenecks.

2. System Architecture

To understand the computational challenges of modern supercomputing, we must first analyze the fundamental computer architectures that govern processor hardware design. Virtually all digital computers constructed over the past eight decades trace their heritage back to the seminal stored-program models developed in the 1940s.

2.1 The Von Neumann Model & Bottleneck

In 1945, mathematician John von Neumann proposed an architectural framework where both executable program instructions and raw dataset values share a single physical main memory unit (RAM). In a pure Von Neumann architecture, a shared system bus—comprising address lines, data lines, and control signals—acts as the single highway connecting the Central Processing Unit (CPU) to main memory and peripheral I/O devices.

Figure 1: The Von Neumann Architecture — a shared bus connects CPU, Memory, and I/O.

While elegant and simple to program, this shared bus design induces a severe physical constraint known as the Von Neumann Bottleneck. Because instructions and data must travel over the exact same physical wires, the CPU cannot read an instruction opcode and access a data operand simultaneously. As microprocessor clock frequencies accelerated exponentially into the gigahertz realm over recent decades, memory bus throughput lagged behind. Consequently, high-performance CPU cores spend a substantial percentage of their operational clock cycles in a stalled state, waiting for data to travel over the congested memory bus.

2.2 The Harvard Architecture & Modern Hybrid Implementations

Developed for the Harvard Mark I electromechanical computer, the Harvard Architecture directly resolves bus contention by physically segregating instruction memory from data memory. By providing separate, dedicated address and data buses for instructions and data, a Harvard processor can simultaneously read an instruction from instruction memory and perform a read or write operation on data memory within a single clock cycle.

In modern High Performance Computing, pure Harvard architectures are rarely deployed for primary main memory due to the complexity of managing rigid, separate memory banks. Instead, enterprise server microprocessors—such as AMD EPYC and Intel Xeon CPUs—implement a Modified Harvard Architecture. Externally, the operating system views a single, unified main memory (DRAM) address space for programmatic simplicity. Internally on the silicon die, however, the CPU core maintains physically distinct L1 Instruction (L1i) and L1 Data (L1d) caches. This hybrid design delivers simultaneous instruction fetching and data processing at core clock speeds while preserving the flexibility of a unified system memory model.

3. The Memory Wall and Caching

3.1 The Memory Wall Problem

For more than three decades, microprocessor raw performance scaled exponentially in accordance with Moore's Law and Dennard Scaling, increasing by approximately 55% per year. In contrast, Dynamic Random-Access Memory (DRAM) access latencies improved at a far slower rate of less than 7% annually. This widening performance gap between execution speed and memory retrieval speed is formally termed the Memory Wall.

Figure 2: The Memory Wall — widening gap between CPU clock rate and DRAM access speed.

To grasp the severity of the Memory Wall in HPC workloads, consider a modern CPU core operating at a 4.0 GHz clock frequency. Each execution clock cycle completes in a mere 0.25 nanoseconds. However, requesting a data line from main DRAM memory requires approximately 80 to 100 nanoseconds. Without intermediate caching mechanisms, the CPU core would idle for roughly 350 to 400 clock cycles on every single memory miss. In large-scale scientific simulations involving billions of floating-point matrix transformations, this delay completely degrades theoretical CPU performance.

3.2 Solution: Cache Hierarchies & Locality Principles

To overcome the Memory Wall, modern computer architects employ multi-tiered cache hierarchies designed around the fundamental software principles of locality:

Temporal Locality dictates that data or instructions accessed at one point in time are highly likely to be accessed again in the immediate future (e.g., variables inside iterative for loops or frequently invoked subroutine instructions). Spatial Locality dictates that when a specific memory address is accessed, adjacent memory locations are highly likely to be accessed soon (e.g., traversing consecutive elements of a contiguous array or matrix row).

Processor architects exploit these locality principles by placing small, ultra-fast Static RAM (SRAM) cache layers between the execution cores and main DRAM memory:

The Level 1 (L1) Cache sits directly inside the execution pipeline of each individual core. Operating at full CPU clock frequency, it is split into dedicated L1 Instruction (L1i) and L1 Data (L1d) caches (typically 32 KB to 64 KB each) delivering access latencies of 1.0 to 1.5 nanoseconds (3 to 4 clock cycles).

The Level 2 (L2) Cache serves as a larger, dedicated fallback buffer private to each individual core (typically 512 KB to 1 MB per core). Operating with access latencies of 3 to 4 nanoseconds (12 to 14 clock cycles), the L2 cache catches requests that miss L1 before they hit shared interconnects.

The Level 3 (L3) Last-Level Cache (LLC) is shared across a cluster of cores on a silicon complex (CCX/CCD). Modern HPC processors feature massive L3 caches ranging from 32 MB to over 1 GB (utilizing 3D vertical stacking technologies). Operating at 10 to 15 nanoseconds (40 to 50 clock cycles), the L3 cache intercepts off-chip requests, preserving precious main memory bandwidth for inter-node MPI operations.

4. Processor Architecture & Flynn's Taxonomy

4.1 Flynn's Taxonomy of Parallel Architectures

In 1966, computer architect Michael J. Flynn introduced a formal classification scheme for computer architectures based on the number of concurrent instruction streams and data streams processed by the hardware.

Figure 3: Flynn's Taxonomy — SISD, SIMD (vectorization/GPU), MISD, and MIMD (clusters).

Single Instruction, Single Data (SISD) describes traditional single-core scalar computers. A single processor executes a single sequential instruction stream acting on a single data stream in main memory. Classic single-core x86 systems fit this category.

Single Instruction, Multiple Data (SIMD) describes architectures where a single instruction stream operates simultaneously across multiple distinct data elements in parallel. SIMD forms the mathematical engine of modern HPC, powering CPU vector execution units (AVX-512, ARM SVE) and Graphics Processing Units (GPUs), where thousands of arithmetic lanes execute identical matrix operations across broad data arrays in parallel.

Multiple Instruction, Single Data (MISD) describes systems where multiple distinct instruction streams operate simultaneously on a single shared data stream. Although rare in general scientific computing, MISD is utilized in mission-critical, fault-tolerant environments—such as flight control systems, nuclear reactor safeguards, and space systems—where redundant execution paths process identical sensor data to verify hardware consensus.

Multiple Instruction, Multiple Data (MIMD) represents the dominant architecture of modern supercomputers and HPC clusters. In a MIMD system, multiple independent processors or compute nodes simultaneously execute distinct instruction streams on distinct data sets. MIMD divides into two primary paradigms: Shared-Memory MIMD (multi-socket NUMA servers running multi-threaded OpenMP applications) and Distributed-Memory MIMD (multi-node clusters coordinating computational ranks via MPI over high-speed InfiniBand interconnects).

4.2 Amdahl's Law vs Gustafson's Law

Predicting parallel performance gains requires understanding the mathematical laws governing speedup limits under different scaling conditions.

Amdahl's Law (Strong Scaling) evaluates speedup when solving a fixed problem size ($W$) across an increasing number of processor cores ($N$). If a fraction $(1-p)$ of an algorithm is inherently serial and cannot be parallelized, Amdahl's Law establishes a strict mathematical upper bound on total speedup $S$:

$$ S = \frac{1}{(1-p) + \frac{p}{N}} $$

Even if an infinite number of processors ($N \to \infty$) are applied, the maximum attainable speedup can never exceed $\frac{1}{1-p}$. For example, if just 5% of a program is strictly serial ($1-p = 0.05$), the maximum theoretical speedup is capped at 20$\times$, regardless of whether 100 or 100,000 CPU cores are deployed.

Gustafson-Barsis's Law (Weak Scaling) addresses Amdahl's limitation by recognizing that in real-world HPC scientific applications, researchers do not keep the problem size fixed when given a larger supercomputer. Instead, as processor counts expand, the problem size is expanded proportionally to occupy the available parallel hardware and memory. Gustafson's Law models scaled speedup $S_p$ under constant execution time:

$$ S_p = N - (1-p)(N-1) = s + pN $$

Gustafson's Law demonstrates that for large-scale scientific problems where the parallel workload grows alongside processor availability, massive supercomputers containing tens of thousands of cores achieve near-linear parallel speedup.

5. Career Pathways & Self-Assessment

Mastering High Performance Computing fundamentals prepares students for high-impact engineering careers across the tech industry. Specialized HPC roles include HPC Systems Engineers (designing supercomputing clusters and InfiniBand fabrics), Cloud Infrastructure Architects (building scalable cloud compute pools), Site Reliability Engineers (SRE) (ensuring large-scale system availability), and Research Software Engineers (RSE) (optimizing scientific code for national supercomputing facilities).
