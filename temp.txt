168: <h2>Overview</h2>
169: <p>In Week 2, we manually configured the essential services (DHCP, TFTP) required to boot a single machine over the network. While educational, manual configuration does not scale to clusters with hundreds or thousands of nodes. This week, we introduce <strong>Warewulf 4</strong>, a modern cluster provisioning system that automates the deployment and management of operating systems across large-scale infrastructure.</p>
170: <p>Unlike traditional management tools that rely on installing an OS into a hard drive (Stateful), Warewulf specializes in <strong>Stateless Provisioning</strong>, where nodes boot a lightweight, pre-configured operating system directly into RAM. Warewulf 4 represents a significant architectural shift from its predecessors by adopting the <strong>OCI (Open Container Initiative)</strong> standard, allowing administrators to manage compute node images using standard tools like Docker or Podman.</p>
171: <blockquote>
172: <p><strong>Note</strong>: This module focuses on applied provisioning of on-premise HPC clusters typical of institutional and enterprise environments, rather than hyperscale or exascale systems.</p>
173: </blockquote>

184: <h2>1. The Provisioning Problem (Sterling Chapter 5 Extension)</h2>
185: <p>Managing a high-performance cluster presents a unique system administration challenge: <strong>Scale</strong>. Installing an operating system on one server is a trivial task; installing, patching, and maintaining consistent configurations across 500 servers is a massive logistical burden. If a cluster administrator had to physically insert a USB drive or manually run an installer on every node, the cluster would never be operational.</p>
186: <p>Furthermore, consistency is paramount. In an HPC cluster, every Compute Node must be mathematically identical. If Node 01 has <code>libmath-v1.2</code> and Node 02 has <code>libmath-v1.3</code>, a parallel simulation running across both might produce nondeterministic or erroneous results. We require a mechanism that ensures every node runs the exact same software stack, bit-for-bit, every time it boots.</p>
187: <h3>1.1 Power Management (IPMI)</h3>
188: <p>Before a node can be provisioned, it must be powered on. In a data center, sending a technician to physically press a power button on 1,000 servers is impractical. To address this, enterprise servers are equipped with a <strong>Baseboard Management Controller (BMC)</strong>—a specialized service processor that runs independently of the main CPU and OS. This controller implements the <strong>Intelligent Platform Management Interface (IPMI)</strong> protocol, allowing administrators to remotely control power states (On, Off, Cycle) and view serial consoles over the network. Warewulf integrates with IPMI to automate this process, allowing a single command (<code>wwctl power on node[01-99]</code>) to boot the entire cluster simultaneously.</p>
189: <h3>1.2 Stateless Clustering</h3>
190: <p>To solve the scale and consistency problems, HPC clusters typically adopt a <strong>Stateless</strong> architecture. In this model, the Compute Nodes do not have persistent operating systems installed on their local hard drives. Instead, the OS exists as a compressed image on the Controller Node. When a Compute Node powers on, it downloads this image into its Main Memory (RAM) and runs from there.</p>
191: <p>This approach offers three critical advantages. First, <strong>Speed</strong>: Running the OS from RAM is significantly faster than reading from a mechanical hard drive or even an SSD. Second, <strong>Immutability</strong>: A reboot wipes the slate clean. If a user crashes the node or corrupts a system file, a simple reboot restores the node to its pristine "Golden State." Third, <strong>Manageability</strong>: To update the entire cluster, the administrator simply updates the single Golden Image on the Controller Node, rebuilds the container, and reboots the cluster. There is no need to run <code>dnf update</code> on 1,000 separate machines.</p>

193: <h2>2. Warewulf 4 Design and Architecture</h2>
194: <p>Warewulf is the standard open-source provisioning tool for HPC. Version 4 is a complete rewrite in the Go programming language, designed to leverage the modern ecosystem of Containers.</p>
195: <h3>2.1 Design Tenets</h3>
196: <p>Warewulf 4 is built on several core tenets (<a href="https://warewulf.org/">Warewulf.org</a>):</p>
197: <table>
198: <thead>
199: <tr>
200: <th style="text-align: left;">Tenet</th>
201: <th style="text-align: left;">Description</th>
202: </tr>
203: </thead>
204: <tbody>
205: <tr>
206: <td style="text-align: left;"><strong>Lightweight</strong></td>
207: <td style="text-align: left;">Provisions stateless images and leaves no running agents consuming resources.</td>
208: </tr>
209: <tr>
210: <td style="text-align: left;"><strong>Agnostic</strong></td>
211: <td style="text-align: left;">Supports any Linux distribution (Rocky, Alma, Ubuntu, SUSE) on any hardware (x86, ARM).</td>
212: </tr>
213: <tr>
214: <td style="text-align: left;"><strong>Stateless</strong></td>
215: <td style="text-align: left;">Default mode runs entirely in RAM, ensuring nodes always return to a known-good state on reboot.</td>
216: </tr>
217: <tr>
218: <td style="text-align: left;"><strong>Secure</strong></td>
219: <td style="text-align: left;">Supports SELinux out-of-the-box.</td>

221: </tbody>

223: <h3>2.2 The Move to OCI Containers</h3>
224: <p>Previous versions of Warewulf used a custom format called a Virtual Node File System (VNFS), which was difficult to create and maintain. Warewulf 4 adopts the industry-standard <strong>OCI (Open Container Initiative)</strong> format. This means the operating system image that boots your compute nodes is effectively a standard container, identical to those used in Docker or Kubernetes.</p>
225: <blockquote>
226: <p><strong>Note</strong>: Although Warewulf uses OCI containers, these are full operating system images (including systemd, kernels, and shells), not minimal application containers like those used to deploy microservices.</p>
227: </blockquote>
228: <p>Administrators can pull a base image (e.g., <code>docker://rockylinux:9</code>) from a public registry, install HPC libraries into it using standard tools, and then <strong>distribute</strong> that container out to the nodes as a bootable OS.</p>
229: <h4>2.2.1 Image Creation Workflow</h4>
230: <p>The process of preparing a Node Image follows a standard "Import → Customize → Build" lifecycle:</p>
231: <ol>
232: <li><strong>Import</strong>: The administrator pulls a generic "Base Image" (like Rocky Linux 9) from Docker Hub. This image is pristine and contains no cluster-specific configurations.<ul>
233: <li><em>Command</em>: <code>sudo wwctl container import docker://rockylinux:9 rocky-9</code></li>
234: </ul>
235: </li>
236: <li><strong>Customize</strong>: The administrator enters the container (using a chroot shell) to install necessary packages such as the Slurm client, InfiniBand drivers, and compilers.<ul>
237: <li><em>Command</em>: <code>sudo wwctl container shell rocky-9</code></li>
238: </ul>
239: </li>
240: <li><strong>Build</strong>: Once the container is ready, it is "built" (compressed) into a deployable artifact that the Controller can serve via HTTP. This step prepares the image for network booting.<ul>
241: <li><em>Command</em>: <code>sudo wwctl container build rocky-9</code></li>
242: </ul>
243: </li>
244: </ol>

285: <h3>2.4 The Daemon Configuration (warewulf.conf)</h3>
286: <p>The behavior of the Warewulf controller is governed by the global configuration file located at <code>/etc/warewulf/warewulf.conf</code>. This YAML file is the "Single Source of Truth" for how <code>warewulfd</code> interacts with the network and services.</p>
287: <p>This file is divided into several specific sections. Below is a detailed breakdown of the critical parameters you will encounter.</p>
288: <h4>2.4.1 General &amp; Network Settings (<code>warewulf</code> and top-level)</h4>
289: <p>These settings define the Controller node's identity on the private cluster network. Since the Controller acts as the default gateway, DNS server, and boot server for all compute nodes, it is critical that this IP address is static and reachable by the nodes during the PXE boot process. Warewulf uses this specific interface to listen for DHCP requests and serve the operating system images.</p>

Instead of manually editing <code>/etc/dhcp/dhcpd.conf</code> or <code>/etc/exports</code>, you define the desired state in <code>warewulf.conf</code>. When you run <code>wwctl configure -a</code>, Warewulf reads its internal database of nodes and rewrites the configuration files for these services, ensuring they are perfectly synchronized with your cluster inventory.</p>

This is essential for adhering to site-specific storage policies, such as keeping large container images on specific high-capacity partitions (e.g., separate from the root filesystem) or strictly following the Filesystem Hierarchy Standard (FHS).</p>

427: <h3>2.5 The All-in-One Service: dnsmasq</h3>
428: <p>In OpenHPC 4.0, <strong>dnsmasq</strong> is the default provider for Infrastructure Services (DHCP, TFTP, and DNS).</p>
429: <h4>2.5.1 Why dnsmasq?</h4>
430: <p>Unlike traditional enterprise setups that run separate, heavy daemons for each service (e.g., BIND for DNS, ISC-DHCP for IP assignment, and tftpd-hpa for boot files), <code>dnsmasq</code> combines all three into a single, lightweight binary.</p>
431: <ul>
432:     <li><strong>Simplicity</strong>: One configuration file (<code>/etc/dnsmasq.conf</code>) handles everything.</li>
433:     <li><strong>Integration</strong>: It automatically reads <code>/etc/hosts</code> to provide DNS resolution for the cluster.</li>
434: </ul>
435: <h4>2.5.2 Configuration Strategy</h4>
436: <p>If you choose to use <code>dnsmasq</code>, you must <strong>disable</strong> the system-managed DHCP and TFTP in <code>warewulf.conf</code> (set <code>enabled: false</code>) to prevent conflicts.</p>
437: <p><strong>Sample <code>/etc/dnsmasq.conf</code>:</strong></p>
438: <pre><code class="language-ini"># Only listen on the internal cluster interface
439: interface=eth1
440: bind-interfaces
441: 
442: # DHCP Settings
443: dhcp-range=10.0.0.50,10.0.0.99,12h
444: dhcp-option=option:router,10.0.0.1
445: 
446: # TFTP Settings (for PXE Boot)
447: enable-tftp
448: tftp-root=/var/lib/tftpboot
449: dhcp-boot=undionly.kpxe
450: </code></pre>
451: <p>For this course, we will use <strong>dnsmasq</strong> to simplify our lab deployment. This means in your <code>warewulf.conf</code>, you will see <code>dhcp: enabled: false</code> because we are manually managing the <code>dnsmasq</code> service.</p>
452: <hr />
453: <h2>3. The Provisioning Process</h2>
454: <p>When a cluster node boots from Warewulf, it follows a strict sequence of events:</p>
455: <ol>
456: <li><strong>Firmware Initialization</strong>: The BIOS/UEFI initializes hardware and the network card.</li>
457: <li><strong>DHCP Request</strong>: The node broadcasts "Who am I?". The Warewulf server responds with an IP and a "Next-Server" option.</li>
458: <li><strong>iPXE Boot</strong>: The node downloads the <strong>iPXE</strong> network bootloader via TFTP. Unlike legacy PXE, iPXE understands HTTP.</li>
459: <li><strong>Container Fetch</strong>: iPXE contacts the Warewulf Controller (warewulfd) via HTTP to download the Kernel and the OCI Container Image.</li>
460: <li><strong>Overlay Injection</strong>: Warewulf injects the "Overlays" (custom configs like <code>/etc/hostname</code>) into the container in RAM.</li>
461: <li><strong>Switch Root</strong>: The kernel switches from the initramfs to the full container root filesystem, and the node is ready.</li>
462: </ol>
463: <p><strong>Visual Boot Flow</strong>:</p>
464: <p><img alt="Warewulf Provisioning Flow" src="images/warewulf_provisioning_flow.png" />
465: <em>Figure 3.1: The Warewulf 4 Stateless Provisioning Boot Process.</em></p>
466: <p>Warewulf supports <strong>Two-Stage Provisioning</strong> (using a small <code>dracut</code> image first) for efficiency, but for this course, we treat the process as a seamless boot.</p>

572: <hr />
573: <h2>5. Configuration Management: Overlays</h2>
574: <p>A predefined container image solves the bulk of the provisioning problem, but it creates a new one: <strong>Uniqueness</strong>. While 99% of the OS should be identical across all nodes (the kernel, the libraries, the applications), 1% must be unique. For example, every node needs a unique Hostname and a unique IP Address. If every node booted the exact same container, they would all try to be <code>localhost</code> at <code>127.0.0.1</code>.</p>
575: <p>Warewulf solves this with <strong>Overlays</strong>. An overlay is a set of files generated dynamically by the Controller Node and injected into the container image at boot time. The <strong>System Overlay</strong> contains files that must be unique per node, such as <code>/etc/hostname</code>, <code>/etc/hosts</code>, and <code>/etc/NetworkManager/system-connections/</code>. The <strong>Runtime Overlay</strong> is used to update user accounts, password files (<code>/etc/passwd</code>, <code>/etc/shadow</code>), and SSH keys across the cluster while the nodes are running, without requiring a reboot.</p>
576: <p><strong>Example Command</strong>:</p>
577: <pre><code class="language-bash"># List all available overlays
578: sudo wwctl overlay list
579: 
580: # View the template for the hosts file
581: sudo wwctl overlay show system /etc/hosts
582: </code></pre>
583: <p>When a node boots, it first loads the generic Container Image (the heavy lifting). Then, it applies the Overlays (the customization) on top of the filesystem in RAM. This allows a single generic image to service thousands of unique nodes.</p>

634: <h2>7. Troubleshooting Common Issues</h2>
635: <p>Provisioning is complex because it relies on the perfect synchronization of multiple services (DHCP, TFTP, HTTP). Failures often fall into two categories: getting the node to boot (Network), and getting the OS to run (Configuration).</p>
636: <h3>7.1 Network &amp; Boot Phase Failures</h3>
637: <p>These errors occur early in the boot process, usually before the Linux kernel has loaded. They almost always indicate a service failure (DHCP/TFTP) or a firewall blocking traffic.</p>
638: <table>
639: <thead>
640: <tr>
641: <th style="text-align: left;">Symptom</th>
642: <th style="text-align: left;">Probable Cause</th>
643: <th style="text-align: left;">Corrective Action</th>
644: </tr>
645: </thead>
646: <tbody>
647: <tr>
648: <td style="text-align: left;"><strong>"Searching for DHCP..."</strong><br><em>(Infinite Loop)</em></td>
649: <td style="text-align: left;"><code>dnsmasq</code> service is not running or the node is on the wrong interface.</td>
650: <td style="text-align: left;">1. Check status: <code>sudo systemctl status dnsmasq</code><br>2. Check logs: <code>tail -f /var/log/messages</code><br>3. Verify IP: <code>ip addr show eth1</code> matches config.</td>
651: </tr>
652: <tr>
653: <td style="text-align: left;"><strong>"Connection Refused"</strong><br><em>(iPXE Error)</em></td>
654: <td style="text-align: left;">Firewall is blocking Warewulf (9873), TFTP (69), or DHCP.</td>
655: <td style="text-align: left;"><strong>Open required ports</strong>:<br><code>sudo firewall-cmd --add-service=dns --permanent</code><br><code>sudo firewall-cmd --add-service=dhcp --permanent</code><br><code>sudo firewall-cmd --add-service=tftp --permanent</code><br><code>sudo firewall-cmd --add-port=9873/tcp --permanent</code><br><code>sudo firewall-cmd --reload</code></td>
656: </tr>
657: </tbody>
658: </table>
659: <h3>7.2 Image &amp; Configuration Failures</h3>
660: <p>These errors occur after the node has successfully downloaded the kernel. They indicate problems with the container image itself or the configuration overlays.</p>
661: <table>
662: <thead>
663: <tr>
664: <th style="text-align: left;">Symptom</th>
665: <th style="text-align: left;">Probable Cause</th>
666: <th style="text-align: left;">Corrective Action</th>
667: </tr>
668: </thead>
669: <tbody>
670: <tr>
671: <td style="text-align: left;"><strong>"Dracut Timeout"</strong><br><em>(Kernel Panic)</em></td>
672: <td style="text-align: left;">The container image is missing hardware drivers (e.g., InfiniBand or specific Ethernet).</td>
673: <td style="text-align: left;">1. Shell into container: <code>sudo wwctl container shell rocky-9</code><br>2. Install drivers: <code>dnf install kernel-modules-extra</code><br>3. Rebuild: <code>sudo wwctl container build rocky-9</code></td>
674: </tr>
675: <tr>
676: <td style="text-align: left;"><strong>Wrong Hostname / Old IP</strong><br><em>(Stale State)</em></td>
677: <td style="text-align: left;">Database changes were made (e.g., <code>wwctl node set</code>) but Overlays were not rebuilt.</td>
678: <td style="text-align: left;"><strong>Rebuild Overlays</strong>:<br><code>sudo wwctl overlay build</code><br>Reboot the node.</td>
679: </tr>
680: </tbody>
681: </table>
