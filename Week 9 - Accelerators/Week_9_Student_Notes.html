1. Rationale & The Complexity of Parallel Bugs

Debugging parallel software is fundamentally more complex than debugging sequential code. In distributed-memory or multithreaded systems, subtle non-deterministic timing variations, race conditions, deadlocks, and memory corruption create transient defects—frequently referred to as **"Heisenbugs"**—that change behavior or disappear entirely when launched inside a standard interactive debugger.

2. Taxonomy of Parallel Failure Modes (Chapter 14)

Defect CategoryUnderlying Root Cause MechanismManifestation & Risk Profile
Data Race ConditionUnsynchronized concurrent reads and writes to a shared RAM address by multiple OpenMP threads.Non-deterministic output calculations, silent numerical corruption.
DeadlockCircular wait dependency where Process 0 waits for Process 1 while Process 1 waits for Process 0 in blocking calls.Application hangs indefinitely at 0% CPU utilization.
Memory Leak & OOBWriting beyond array allocations (buffer overflow) or failing to free dynamically allocated heap memory across ranks.Segmentation Faults (SIGSEGV) or system memory exhaustion (OOM).
Communication DeadlockMismatched blocking MPI_Send and MPI_Recv buffer tags across ranks.Cluster node starvation; Slurm job walltime timeout.

3. Compiler Instrumentation & Sanitizers

3.1 Compiler Debug Flags

To preserve stack frame pointers and line symbol maps without optimizer reordering distortion:

Terminal 
# Standard GNU C compiler debug invocation for MPI/OpenMP
mpicc -g -O0 -fno-omit-frame-pointer my_parallel_app.c -o my_parallel_app

3.2 Modern Compiler Sanitizers (Address & Thread Sanitizers)

Modern compilers (GCC / Clang) build instrumentation checks directly into binary instruction streams:

Terminal 
# Detect memory corruptions, buffer overflows, and use-after-free errors
mpicc -g -O1 -fsanitize=address my_app.c -o my_app_asan

# Detect OpenMP data races at runtime
gcc -g -O1 -fsanitize=thread -fopenmp my_omp.c -o my_omp_tsan

# Detect undefined integer overflows and invalid pointer arithmetic
gcc -g -O1 -fsanitize=undefined my_app.c -o my_app_ubsan

4. GNU Debugger (GDB) Multi-Thread & Multi-Rank Workflows

4.1 Core GDB Command Reference

GDB CommandSyntax ExampleOperational Action Executed
breakbreak main or break my_file.c:42Sets an execution breakpoint at a function entry or line number.
watchwatch my_varSets a hardware watchpoint that pauses execution whenever my_var is written to.
info threadsinfo threadsDisplays all active threads, their IDs, and current execution frame points.
threadthread 3Switches GDB focus to Thread 3 context.
backtracebacktrace full (or bt)Displays full call stack frames including local variable values.

4.2 Attaching GDB to MPI Ranks inside Slurm

Terminal 
# Launch GDB attached to a running MPI rank process ID
gdb -p $(pgrep my_mpi_app | head -n 1)

6. Core Dumps & System Post-Mortem Analysis

When an unhandled SIGSEGV occurs, Linux can generate a core memory dump for post-mortem analysis:

Terminal 
# Enable unlimited core dump size
ulimit -c unlimited

# Inspect generated core dump with GDB
gdb ./my_app core.12345 -ex "bt full" -ex "quit"
