1. Shared-Memory Architecture (SMP & NUMA)

1.1 Foundations of Symmetric Multiprocessing (SMP)

Before scaling computational workloads across multi-node network clusters, HPC engineers must optimize shared-memory parallelism on single multi-socket server nodes. A Symmetric Multiprocessor (SMP) system consists of two or more identical physical processor sockets connected to a common, shared main memory space and governed by a single operating system kernel.

In modern server microprocessors (such as AMD EPYC and Intel Xeon Scalable processors), dozens or hundreds of physical cores reside on a single silicon substrate. Each physical core possesses private L1 and L2 caches, while sharing a last-level cache (L3) and integrated memory controllers.

1.2 Memory Architectures: UMA vs. NUMA

In legacy UMA architectures, all CPU cores connect to a single centralized memory controller over a shared system bus. Memory access latency is identical regardless of which core executes the read or write instruction. However, as core counts scaled beyond 8 cores, bus contention created severe latency bottlenecks.

Modern enterprise servers split system memory into discrete NUMA Nodes, where each CPU socket or core complex directly controls its local bank of RAM DIMMs:

$$\text{NUMA Distance Ratio} = \frac{\text{Latency}_{\text{Remote Node}}}{\text{Latency}_{\text{Local Node}}} \approx 1.5\text{x to } 2.5\text{x}$$

Cores fetching data from local RAM experience low latency (~60 ns) and full memory bus bandwidth. Conversely, cores fetching data from RAM attached to a foreign CPU socket must traverse inter-socket interconnects (AMD Infinity Fabric, Intel UPI), suffering up to 2.5x higher latency (~140 ns) and reduced bandwidth.

2. Cache Coherence & False Sharing

2.1 The MESI & MOESI Protocols

Because multiple CPU cores maintain private L1/L2 caches of shared main memory locations, hardware enforces Cache Coherence using the MESI protocol (Modified, Exclusive, Shared, Invalid) or the MOESI protocol (which adds an Owner state to allow sharing dirty cache lines without memory write-backs).

2.2 The False Sharing Performance Trap

False Sharing occurs when two independent threads executing on separate CPU cores modify independent variables that happen to reside within the same 64-byte cache line. Even though the software logic is independent, the hardware MESI protocol repeatedly invalidates the cache line across both cores (cache line bouncing), causing severe throughput loss.

C++17 Cache Line Alignment Solution 
// Problem: False sharing (both variables reside in the same 64-byte line)
struct BadThreadData {
    uint64_t counter_thread0; // 8 bytes
    uint64_t counter_thread1; // 8 bytes (same 64-byte line!)
};

// Solution: C++17 Explicit Cache Line Alignment (64 Bytes)
struct alignas(64) GoodThreadData {
    uint64_t counter_thread0;
    uint8_t  padding[56]; // Pad out to full 64-byte boundary
};

struct alignas(64) GoodThreadData2 {
    uint64_t counter_thread1;
    uint8_t  padding[56];
};

3. Slurm Workload Manager Architecture

3.1 Why Resource Managers are Essential

In a shared high-performance computing cluster, hundreds of users submit computationally intensive parallel jobs simultaneously. If users launched programs directly on compute nodes without coordination, multiple jobs would collide on the same CPU cores, exhaust physical RAM memory, cause Out-Of-Memory (OOM) kernel panics, and crash the cluster. The Slurm Workload Manager (Simple Linux Utility for Resource Management) serves as the cluster operating system, arbitrating resource allocations and scheduling job queues.

3.2 Slurm Daemon Microarchitecture

Slurm uses a decoupled, agent-based daemon architecture across the cluster:

The Slurm Controller Daemon (slurmctld) runs on the master control node. It acts as the central brain of the cluster, monitoring node availability, managing pending job queues, computing priority scores, and granting resource allocations to users.

The Slurm Node Daemon (slurmd) runs on every compute node. It listens for execution requests from slurmctld, spawns user tasks, monitors CPU and RAM consumption, and interfaces with Linux Control Groups (Cgroups v2) to enforce strict memory and core boundaries.

The Slurm Database Daemon (slurmdbd) records cluster usage statistics, job completion logs, fair-share historical data, and user account limits into a centralized MySQL/MariaDB database.

4. Deep Dive: Enterprise Slurm Configuration Files

4.1 Anatomy of slurm.conf

The central configuration file for Slurm is /etc/slurm/slurm.conf. It must be identical across all controller and compute nodes in the cluster. Below is an exhaustive breakdown of core configuration directives grouped by functional domain:

/etc/slurm/slurm.conf — Annotated Master Configuration 
# ------------------------------------------------------------------
# CLUSTER IDENTIFICATION & CONTROL DAEMON SETTINGS
# ------------------------------------------------------------------
ClusterName=vut-hpc-cluster
SlurmctldHost=master(192.168.56.10)
SlurmUser=slurm
SlurmctldPort=6817
SlurmdPort=6818
AuthType=auth/munge
CryptoType=crypto/munge
StateSaveLocation=/var/spool/slurmctld
SlurmdSpoolDir=/var/spool/slurmd

# ------------------------------------------------------------------
# LOGGING & PROCESS MANAGEMENT
# ------------------------------------------------------------------
SlurmctldLogFile=/var/log/slurm/slurmctld.log
SlurmdLogFile=/var/log/slurm/slurmd.log
SlurmctldPidFile=/var/run/slurmctld.pid
SlurmdPidFile=/var/run/slurmd.pid
SlurmSchedLogFile=/var/log/slurm/slurmsched.log

# ------------------------------------------------------------------
# SCHEDULER & RESOURCE ALLOCATION ALGORITHMS
# ------------------------------------------------------------------
SchedulerType=sched/backfill
SelectType=select/cons_tres
SelectTypeParameters=CR_Core_Memory
ProctrackType=proctrack/cgroup
TaskPlugin=task/cgroup

# ------------------------------------------------------------------
# PRIORITY & FAIR-SHARE WEIGHTING
# ------------------------------------------------------------------
PriorityType=priority/multifactor
PriorityWeightDecayHalfLife=14-0
PriorityWeightFairshare=100000
PriorityWeightAge=10000
PriorityWeightPartition=10000
PriorityWeightJobSize=1000

# ------------------------------------------------------------------
# ACCOUNTING DATABASE INTEGRATION
# ------------------------------------------------------------------
AccountingStorageType=accounting_storage/slurmdbd
AccountingStorageHost=master
AccountingStoragePort=6819
AccountingStorageUser=slurm
AccountingStoreFlags=job_comment,script

# ------------------------------------------------------------------
# COMPUTE NODE & PARTITION DEFINITIONS
# ------------------------------------------------------------------
NodeName=node[01-04] CPUs=2 RealMemory=2048 Sockets=1 CoresPerSocket=2 ThreadsPerCore=1 State=UNKNOWN
NodeName=master      CPUs=2 RealMemory=4096 Sockets=1 CoresPerSocket=2 ThreadsPerCore=1 State=UNKNOWN

PartitionName=standard Nodes=node[01-04] Default=YES MaxTime=24:00:00 State=UP DefMemPerCPU=1024 MaxMemPerCPU=2048
PartitionName=highmem  Nodes=master      Default=NO  MaxTime=04:00:00 State=UP DefMemPerCPU=2048 MaxMemPerCPU=4096

Key Parameter Explanations:

  • AuthType=auth/munge: Uses the Munge authentication daemon to produce cryptographic MUNGE credentials, verifying that IPC requests originate from valid cluster users.
  • SelectType=select/cons_tres: Enables Consumable Trackable Resources, allowing Slurm to track and allocate specific numbers of CPU cores, RAM bytes, and GPU devices independently.
  • SelectTypeParameters=CR_Core_Memory: Configures Slurm to treat both individual CPU Cores and RAM Memory as consumable resources. If a job requests 2GB RAM on a node with 2GB total RAM, no other job can be scheduled on that node even if CPU cores remain idle.
  • TaskPlugin=task/cgroup: Binds spawned user tasks to Linux Control Groups (cgroups), enforcing hardware isolation.

4.2 Anatomy of cgroup.conf

The /etc/slurm/cgroup.conf file governs Linux Kernel Cgroup isolation on compute nodes:

/etc/slurm/cgroup.conf — Linux Cgroup Enforcement Rules 
CgroupAutomount=yes
CgroupReleaseAgentDir="/etc/slurm/cgroup"
ConstrainCores=yes
ConstrainRAMSpace=yes
ConstrainSwapSpace=yes
ConstrainDevices=yes
AllowedRAMSpace=100
AllowedSwapSpace=0

Parameter Explanations:

  • ConstrainCores=yes: Restricts job processes exclusively to the CPU core masks assigned by Slurm. Threads attempting to execute on unallocated cores are blocked by the kernel.
  • ConstrainRAMSpace=yes: Enforces strict physical RAM memory limits. If a user job exceeds its requested RAM allocation (e.g. requesting 1GB but attempting to allocate 3GB), the kernel Out-Of-Memory (OOM) killer immediately terminates the job process, protecting neighboring jobs from memory starvation.
  • ConstrainDevices=yes: Restricts GPU device access so users can only see and access the specific GPU cards assigned to their job.

5. Exhaustive Slurm Command & Parameter Reference

5.1 Batch Job Submission: sbatch Options

The sbatch command parses `#SBATCH` directives in a script and submits the job asynchronously to the Slurm queue. Below is a comprehensive reference table of essential sbatch parameters:

Directive Parameter Example Usage Detailed Operational Purpose
--job-name (-J) #SBATCH --job-name=matrix_mult Assigns a human-readable identifier name displayed in queue listings.
--nodes (-N) #SBATCH --nodes=2 Requests a specific minimum and maximum number of physical compute nodes.
--ntasks (-n) #SBATCH --ntasks=8 Requests total number of parallel tasks (e.g. MPI processes) across all allocated nodes.
--cpus-per-task (-c) #SBATCH --cpus-per-task=4 Allocates CPU cores per task for hybrid OpenMP/MPI applications (sets OMP_NUM_THREADS).
--mem / --mem-per-cpu #SBATCH --mem=4G Specifies real memory requirement per node (--mem=4G) or per CPU core (--mem-per-cpu=1024M).
--time (-t) #SBATCH --time=02:30:00 Sets maximum wall-clock runtime limit (HH:MM:SS or DD-HH:MM:SS). Job is killed if exceeded.
--partition (-p) #SBATCH --partition=standard Submits job to a specific queue partition (e.g. standard, highmem, gpu).
--output / --error (-o / -e) #SBATCH -o out_%j.log -e err_%j.log Redirects standard output (stdout) and standard error (stderr) file paths. %j expands to Job ID.

5.2 Real-Time & Interactive Allocation: srun & salloc

While sbatch is for non-interactive batch jobs, srun and salloc provide real-time interactive access:

Interactive Shell Allocation (salloc): Allocates compute resources in real time and spawns a bash shell on the login node with job environment variables exported:

# Request 1 node with 2 CPUs for 1 hour interactively
salloc --nodes=1 --cpus-per-task=2 --time=01:00:00 --partition=standard

Interactive Terminal Access (srun --pty): Spawns an interactive pseudo-terminal directly inside a compute node environment:

# SSH directly into an allocated compute node shell
srun --nodes=1 --pty /bin/bash

5.3 Queue Inspection & Administrative Diagnostics: squeue, sinfo, scontrol & sacct

Queue Monitoring (squeue)

Displays pending (PD), running (R), and completing (CG) jobs. Advanced custom formatting syntax:

squeue -u student1 -o "%.18i %.9P %.8j %.8u %.2t %.10M %.6D %R"

Node Status Inspection (sinfo)

Summarizes node state codes: idle (available), alloc (fully loaded), mix (partially loaded), drain (maintenance mode), down (offline).

sinfo -N -l

Live Administrative Modification (scontrol)

Allows administrators to inspect detailed job state metadata or dynamically modify running job parameters without killing the job:

# View full internal diagnostic dump of Job 104
scontrol show job 104

# Hold and release a queued job
scontrol hold 104
scontrol release 104

# Dynamically update requested memory allocation
scontrol update JobId=104 MinMemoryCPU=2048

Accounting Log Queries (sacct)

Queries historical job accounting logs from the MySQL database to analyze memory usage and exit status codes:

sacct -j 104 --format=JobID,JobName,Partition,AllocCPUs,Elapsed,State,ExitCode,MaxRSS

6. Hardware Topology Discovery & Thread Pinning

To prevent the Linux kernel OS scheduler from migrating threads across NUMA domains during execution, HPC developers enforce thread binding and CPU affinity:

Terminal — NUMA Discovery & Thread Binding 
# Inspect NUMA hardware topology and distance matrix
numactl --hardware

# Display graphical topology diagram of sockets, NUMA nodes, and caches
lstopo --output-format png > topology.png

# Enforce core binding via Slurm
srun --cpu-bind=cores ./my_app
