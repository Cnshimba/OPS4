1. Foundations of Symmetric Multiprocessing (SMP)

Before scaling computational workloads across multi-node network clusters, HPC engineers must optimize shared-memory parallelism on single multi-socket server nodes. A Symmetric Multiprocessor (SMP) system consists of two or more identical physical processor sockets connected to a common, shared main memory (RAM) space and governed by a single operating system kernel.

2. Component Architecture of Modern Microprocessors (Chapter 6)

Modern server microprocessors (e.g., AMD EPYC 9004/9005 series, Intel Xeon Scalable Granite Rapids) pack up to 128 physical cores onto a single silicon substrate using chiplet designs. Below is the hardware layer hierarchy:

3. UMA vs. NUMA Memory Architectures

3.1 Uniform Memory Access (UMA)

In legacy UMA architectures, all CPU cores connect to a single centralized memory controller over a shared system bus. Memory access latency is identical regardless of which core executes the read or write instruction. However, as core counts scaled beyond 8 cores, bus contention created severe latency bottlenecks.

3.2 Non-Uniform Memory Access (NUMA)

Modern enterprise servers split system memory into discrete **NUMA Nodes**, where each CPU socket or core complex directly controls its local bank of RAM DIMMs:

$$ \text{NUMA Distance Ratio} = \frac{\text{Latency}_{\text{Remote Node}}}{\text{Latency}_{\text{Local Node}}} \approx 1.5\text{x to } 2.5\text{x} $$
  • Local Memory Read: Cores fetching data from local RAM experience low latency (~60 ns) and full bus bandwidth (~300 GB/s per socket).
  • Remote Memory Read: Cores fetching data from RAM attached to a foreign socket must traverse inter-socket interconnects (AMD Infinity Fabric, Intel UPI), suffering up to 2.5x higher latency (~140 ns) and reduced available bandwidth.

4. Cache Coherence Protocols: MESI & MOESI

Because multiple CPU cores maintain private L1/L2 caches of shared main memory locations, hardware must enforce **Cache Coherence** so no core reads stale data.

4.1 The MESI Protocol (4 States)

State NameMeaning & Ownership PropertyIs RAM Up to Date?
M (Modified)Cache line is present only in the current core's cache and has been written to (dirty). The core must write back to RAM before eviction.No (RAM contains stale data).
E (Exclusive)Cache line is present only in the current core's cache and has not been written to (clean).Yes (Matches RAM).
S (Shared)Cache line is present in multiple cores' private caches in clean read-only state.Yes (Matches RAM).
I (Invalid)Cache line contains invalid/stale data and cannot be read.N/A

4.2 The MOESI Extension

The MOESI protocol adds an O (Owner) state. The Owner state allows a core to hold a dirty cache line while sharing read access with other cores without writing the line back to main RAM, preserving precious memory bus bandwidth.

5. The False Sharing Performance Trap

False Sharing occurs when two independent threads executing on separate CPU cores modify independent variables that happen to reside within the same 64-byte cache line. Even though the software logic is independent, the hardware MESI protocol repeatedly invalidates the cache line across both cores ("cache line bouncing"), causing up to a 90% drop in computational throughput.

Terminal 
// Problem: False sharing (both variables reside in the same 64-byte cache line)
struct BadThreadData {
    uint64_t counter_thread0; // 8 bytes
    uint64_t counter_thread1; // 8 bytes (Resides in same 64-byte line!)
};

// Solution: C++17 Explicit Cache Line Alignment (64 Bytes)
struct alignas(64) GoodThreadData {
    uint64_t counter_thread0;
    uint8_t  padding[56]; // Pad out to full 64-byte boundary
};

struct alignas(64) GoodThreadData2 {
    uint64_t counter_thread1;
    uint8_t  padding[56];
};

6. Hardware Topology Discovery & Thread Pinning

To prevent the Linux kernel OS scheduler from migrating threads across NUMA domains during execution, HPC developers enforce thread binding and CPU affinity:

Terminal 
# Inspect NUMA hardware topology, node distance matrices, and core mapping
numactl --hardware

# Display graphical topology diagram of sockets, NUMA nodes, and caches
lstopo --output-format png > topology.png

# Launch process bound to NUMA node 0 cores and local RAM
numactl --cpunodebind=0 --membind=0 ./my_multithreaded_app

# Enforce core binding via Slurm
srun --cpu-bind=cores ./my_app
