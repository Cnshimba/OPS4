1. Introduction & Operational Rationale

High-Performance Computing (HPC) clusters represent shared multi-tenant infrastructure costing millions of dollars. Compute nodes host tens of thousands of processing cores, terabytes of system memory, and high-speed network switches. Without automated workload management, multi-user cluster environments would instantly descend into operational chaos: processes from different research groups would collide on the same physical CPU cores, compete for system memory, overflow available RAM, and trigger non-deterministic Linux Out-Of-Memory (OOM) kernel panics.

A Resource Manager and Job Scheduler acts as the central operating system kernel of an HPC cluster. It abstracts physical compute hardware into consumable resource pools, tracks node health status, prioritizes pending execution queues according to institutional policies, enforces strict memory and process isolation boundaries, and logs historical resource utilization metrics for auditing and capacity planning.

2. Taxonomy of Managed HPC Resources (Chapter 5)

Slurm (Simple Linux Utility for Resource Management) manages resources across a multi-dimensional matrix:

Resource DomainPhysical EntitySlurm Management Mechanics
NodesIndividual server blades / chassis in compute racks.Grouped into logical partitions (queues). Tracked in real-time states (e.g., IDLE, ALLOCATED, DRAIN, DOWN).
Sockets & CoresPhysical CPU sockets and hardware cores.Allocated via Consumable Resources plugin (select/cons_tres). Bound to processes via cgroups to prevent core contention.
System MemoryRAM DIMMs on compute node mainboards.Enforced as strict memory limits per node (--mem) or per CPU core (--mem-per-cpu). Oversubscription triggers cgroup OOM termination.
Accelerators / GPUsNVIDIA H100/A100 GPUs, AMD Instinct accelerators.Managed as Generic Resources (GRES). Tracks GPU device indices, memory utilization, and PCIe topology affinity.
Interconnect & TopologyInfiniBand switches and optical fabric links.Slurm's topology plugin (topology/tree) schedules multi-node jobs onto nodes attached to the same leaf switch to minimize network hops.

3. Slurm Architecture & Daemon Hierarchy

Slurm uses a resilient, distributed daemon model comprising master control controllers, accounting daemons, node execution agents, and cryptographic authentication protocols:

Daemon ProcessHost LocationCore System Responsibilities
slurmctldMaster Controller NodeThe central brain of the cluster. Manages queue states, evaluates fair-share algorithm math, allocates compute nodes to jobs, and monitors node heartbeats. Supports active/backup failover pairs.
slurmdEvery Compute NodeThe compute node execution agent. Listens for step launch requests from slurmctld, spawns user tasks, creates cgroup containers, attaches CPU masks, and reports local node health.
slurmdbdDatabase Host ServerThe Slurm Database Daemon. Provides a secure gateway between slurmctld and a relational MariaDB database for historical accounting, user bank allocations, and job metrics.
mungedAll Cluster NodesMUNGE (Munge Uid 'N' Gid Environment) service. Generates cryptographic SAML-like payload tokens to authenticate RPC messages between nodes without password prompts.

4. Priority Calculation & Fair-Share Scheduling Mathematics

When multiple users submit jobs simultaneously, Slurm computes a dynamic Job Priority Score for every pending job in the queue using the Multifactor Priority Plugin:

$$ \text{Priority} = (W_{age} \times A) + (W_{fairshare} \times F) + (W_{jobsize} \times S) + (W_{partition} \times P) + (W_{qos} \times Q) $$
  • Age Factor (A): Increases linearly the longer a job remains pending in the queue, preventing job starvation.
  • Fair-Share Factor (F): Measures an account's historical resource consumption relative to its allocated share. Accounts that have under-utilized their quota receive higher fair-share scores; heavy users receive lower priority.
  • Job Size Factor ($S$): Rewards jobs requesting larger node counts to maximize cluster parallel efficiency and throughput.
  • Partition Priority ($P$): Baseline weight assigned to specific queues (e.g., high-priority interactive queues vs. low-priority preemptible queues).

6. Linux Control Groups (cgroups v2) & Memory Isolation

Slurm uses cgroups (Control Groups) to construct isolated kernel containers for every job step. This prevents a single misbehaving process from affecting neighbor tasks on shared nodes:

  • cpu.cfs_quota_us: Hard-limits CPU cycle bandwidth to the exact core count requested by the job script.
  • cpuset.cpus: Binds thread execution strictly to designated physical core IDs, eliminating cross-socket cache bouncing.
  • memory.max: Enforces hard RAM limits. If a process exceeds its requested limit (--mem), the cgroup subsystem terminates the job cleanly with an OUT_OF_MEMORY error.

8. Annotated Production Batch Scripts

8.1 Multi-Node MPI Job Script

Terminal 
#!/bin/bash
#SBATCH --job-name=mpi_fluid_sim
#SBATCH --output=logs/mpi_%j.out
#SBATCH --error=logs/mpi_%j.err
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=4
#SBATCH --cpus-per-task=1
#SBATCH --mem=8000M
#SBATCH --time=02:00:00
#SBATCH --partition=batch

# Environment configuration
module purge
module load gcc/12.2.0 mpi/openmpi-x86_64

# Execute parallel application across 8 total MPI tasks (2 nodes x 4 tasks/node)
srun /shared/apps/fluid_simulation --grid-size=2048

8.2 Hybrid MPI + OpenMP Job Script

Terminal 
#!/bin/bash
#SBATCH --job-name=hybrid_matrix
#SBATCH --output=logs/hybrid_%j.out
#SBATCH --error=logs/hybrid_%j.err
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=2
#SBATCH --cpus-per-task=4
#SBATCH --mem=16000M
#SBATCH --time=01:30:00
#SBATCH --partition=batch

# Configure OpenMP multithreading environment matching allocated cpus-per-task
export OMP_NUM_THREADS=$SLURM_CPUS_PER_TASK
export OMP_PROC_BIND=close
export OMP_PLACES=cores

module load mpi/openmpi-x86_64

# Execute 4 total MPI ranks (2 ranks/node), each launching 4 OpenMP threads (16 total cores)
srun /shared/apps/hybrid_solver
