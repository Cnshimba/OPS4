📋 Overview

An essential responsibility of an HPC systems administrator is evaluating the raw processing capacity and computational efficiency of a cluster. This laboratory guides you through building, tuning, and executing the standard HPC benchmarking suite, High-Performance Linpack (HPL) — the benchmark that structures the international Top 500 list of supercomputers.

Section 1: Lab Overview and Benchmarking Fundamentals

To evaluate cluster scaling, students must analyse the critical difference between theoretical peak performance and actual sustained performance:

MetricDefinitionSignificance
Rpeak (Theoretical Peak)The mathematical maximum performance a system can achieve based on its CPU cores, clock speed, and execution instructions per cycle.Upper bound — never achievable in practice
Rmax (Sustained Performance)The actual measured performance (GFLOPS) achieved by the benchmarking code when solving a massive system of linear equations.Real-world performance metric
Cluster Efficiency (E)E = Rmax / RpeakIdentifies bottlenecks, memory limitations, and compiler tuning discrepancies

1.1 Amdahl's Law and Scaling

Amdahl's Law models the theoretical speedup limit of an application as a function of its sequential (non-parallel) fractions:

Terminal
Terminal Command 
Speedup = 1 / (S + (1 - S) / N)

Where:
  S = serial execution fraction
  N = number of parallel processing ranks

Benchmarking with HPL exposes how memory latency, network throughput (InfiniBand or Ethernet), and MPI messaging overhead affect the parallel scaling curve of distributed systems.

Section 3: Tuning the HPL.dat Configuration File

The performance of HPL depends directly on the configuration parameters in /shared/benchmarks/hpl/HPL.dat. You must size the problem matrix properly to fit the memory constraints of your VMs.

Step 1 – Understanding the Tuning Parameters

ParameterDescriptionGuidance
N (Problem Size)Dimension of the linear system matrix.Size to consume ~80% of total cluster RAM for maximum GFLOPS.
NB (Block Size)Block-cyclic data distribution size.Typically set between 128 and 256 for modern CPU caches.
P × Q (Process Grid)MPI process grid where P × Q = total MPI ranks.For 4 nodes × 2 CPUs = 8 ranks: e.g., P=2, Q=4.

Step 2 – Calculating Memory Constraints and Sizing N

Each compute node has 2048 MB of RAM. Sizing HPL to consume 80% of local memory prevents the kernel from swapping data to disk. We calculate N using:

Terminal
Terminal Command 
Memory (GB) = (N² × 8 bytes/double) / 1024³

For 80% of ~6 GB total active RAM across 4 nodes:
N = sqrt( (6.0 × 1024³ × 0.80) / 8 )
N ≈ 25000

Section 5: Calculating Cluster Efficiency

To evaluate cluster scaling, calculate the theoretical peak performance (Rpeak) of your cluster and compare it to the measured Rmax GFLOPS:

Terminal
Terminal Command 
Rpeak = Nodes × (CPUs per Node) × (Clock Speed GHz) × (FLOPs per Cycle)

Example: 4 nodes × 2 CPUs × 2.4 GHz × 4 FLOPs/cycle = 76.8 GFLOPS

Cluster Efficiency (E) = (Rmax / Rpeak) × 100%
Example: (11.63 / 76.8) × 100% = 15.14%

📌 Top 500 Context

HPL is the exact benchmark used by the Top 500 Supercomputer List. The world's fastest supercomputers achieve efficiencies of 80–95%. A commodity cluster typically achieves 10–30%, limited by Ethernet latency versus InfiniBand, and shared-memory access patterns.

Section 6: Troubleshooting Benchmarking Outages

Symptom / ErrorPossible CauseDiagnostic & Resolution
HPL job crashes with OOM-killMatrix size N is too high, exceeding local node memory.Decrease N in HPL.dat (e.g., to 15000) or check memory with pdsh -a free -h.
Measured GFLOPS drop by 90%HPL parameters triggered disk swapping.Decrease N to ensure data arrays fit entirely within physical RAM boundaries.
Error: Grid P × Q mismatchProcess grid in HPL.dat doesn't match allocated MPI tasks.Ensure P × Q (e.g., 2 × 4 = 8) matches nodes × tasks-per-node = 8.
Compilation fails: libopenblas not foundLAdir path in Make.Rocky points to wrong OpenBLAS location.Verify ls /shared/apps/openblas/lib/libopenblas.so exists.
